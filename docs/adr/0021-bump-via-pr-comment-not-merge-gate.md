# Publishing stays informational until someone bumps, then merge publishes

Publishing on every push to `main` was fine; failing a PR because the version wasn't bumped was not — it punished PRs that had no reason to ship yet. Ticket 69 wired `pnpm publish:jsr` to `main` and a JSR dry-run to the merge gate; that still assumed someone would edit five `package.json` / `jsr.json` files by hand when a real publish was wanted.

`.github/workflows/ci.yml` still runs `check` on push and pull request, and `jsr-dry-run` on `pull_request` so a package that cannot publish cannot merge. A new `publish-preview` job on pull requests only comments (never fails) on whether this PR's published-file changes are already shipped, ready to ship, or waiting on a bump — and mentions `/bump` even when there's nothing to ship yet, so it stays discoverable.

Bumping happens on the PR itself via `.github/workflows/bump.yml`: commenting `/bump` (default patch) or `/bump minor` / `/bump major` on a PR runs `scripts/bump.ts` and pushes a lockstep version bump across all five `@speechdeck/*` packages to that branch, so review and CI re-run against the real version that will ship. The branch's own `jsr.json` can be stale by then — another PR may have bumped and merged to `main` after this branch was cut — so the workflow reads `origin/main`'s `packages/core/jsr.json` version first and passes it as `--baseline`; `bump()` bumps from whichever is higher, the branch's own version or that baseline, instead of trusting a possibly-stale checkout.

`.github/workflows/publish.yml` runs on every push to `main` but checks `scripts/should-publish.ts` first and skips quietly if every package's version is already on JSR, so an unbumped merge is a no-op, not a failure. `scripts/publish-jsr.mjs` also skips a package whose version is already on JSR (except `--dry-run`), so a partial publish can be retried without failing on the packages that already landed. Bump and publish are separate workflow files from CI specifically so a PR's checks list only ever shows jobs that apply to a PR — no confusing "skipped" entries for jobs that only run on a comment or a push to `main`.

Rejected: independent per-package versions (one `/bump` would be ambiguous, and workspace pins at publish time already lock the five together); failing CI when published files changed without a bump (ReadyRun's lesson: that punishes docs-and-test PRs); a `workflow_dispatch` button (it only exists at the repo's Actions tab with no link back to the PR).
